# Engineering decisions

1. **Reference release, fail-closed production.** This empty repository contained no prototype. The supplied spec is preserved verbatim in SPEC.md. Version 0.1.0 implements a testable foundation and synthetic workflow; incomplete controls are listed in STATUS.md. `EXCHANGE_MODE=production` refuses startup, including when HSM hardware is unavailable. No production readiness or certification is implied.
2. **One checkout.** Develop in the existing task checkout; do not create an additional worktree unless explicitly requested.
3. **Strict data separation boundary.** The UI workflow is explicitly a synthetic local sandbox. No real bank adapters are wired into it. Independent peer listeners only dispatch approved catalog questions; unimplemented actions are refused. The local API is never mounted on a peer listener. Completing distributed actions requires a separate integration milestone.
4. **Persistence.** SQLAlchemy supports SQLite for local demonstrations and PostgreSQL for pilots. Reference records use typed keys and JSON snapshots instead of the final canonical normalized schema. A node-level PostgreSQL advisory transaction lock serializes mutations across workers; SQLite uses `BEGIN IMMEDIATE` and a process lock. Audit events are hash chained in the same transaction. This simple layout is intentionally not represented as the final migrations/schema or high-throughput implementation.
5. **No automatic retries on financial actions.** The reference creates durable payment intents rather than sending network instructions. There is no automatic export daemon or uncertain-payment retry. Bank deployment needs a transactional outbox dispatcher, execution reconciliation and bank acknowledgments before enabling actions.
6. **Signatures.** RFC 8785 canonicalization, Ed25519 node/officer signatures, X25519+HKDF+HMAC equality checks. Local keys are persisted with mode 0600; software signing is conspicuously development-only. PKCS#11 signing backend is supplied but untested against a bank token. No key material or telemetry is transmitted to a service provider.
7. **Response binding.** Signed peer response bodies wrap the answer with `request_nonce`. The client verifies the response signer, recipient, version, timestamp, trade and initiating nonce. This small protocol extension prevents accepting another valid signed answer as the response to a current request.
8. **Pinned TLS.** TLS 1.3 only; configured peer certificates are the only trust roots, followed by exact DER certificate fingerprint checks against the sender. Self-signed short-lived development certificates are generated only for tests. Bank certificate provisioning and rollover need an approved process.
9. **Officer demo sessions.** Password-gated one-hour bearer sessions, explicit officer selection, no credentials in localStorage (sessionStorage only). All synthetic identities share the local sandbox password. This is not SSO, MFA, individual identity assurance, or a bank access model. Production mode is disabled. No public/API peer access is configured by default.
10. **Approval binding.** Approvals bind action, exact trade terms and document hash, plus KYC package/SSI hashes for those changes. Decision records include officer, timestamp and signature. Distinct officers are enforced for the agent SSI callback control. Documents are checked against the sandbox's booked-trade fixture. Real callback evidence, independent books and legal templates remain integration work.
11. **Money.** Python uses integer cents and Decimal strings with half-up rounding; no binary float is used for backend valuation. The demonstration amounts are within RFC 8785/I-JSON's safe integer range. Full int64 wire support requires representing amounts outside ±(2^53−1) as Decimal strings before enabling bank adapters. The UI formats reference values in USD and receives no raw SSI/KYC.
12. **Payment artifacts.** A reference pacs.008 builder and constrained camt.054 parser are provided. XSD validation requires a supplied bank/ISO scheme XSD and does not silently skip checks. Neither is enabled as a live payment integration. The demo booked-credit endpoint exists only in the demo-only API and is clearly marked synthetic.
13. **Bank templates and approvals.** The supplied template is clearly non-operative; no legal terms were invented. No admin catalog changes, peer onboarding, update approvals or external notifications are simulated as production features.
14. **Performance evidence.** Local synthetic timings and loopback TLS timings are reported separately, with sample counts and scope. They do not establish WAN p95, 20 concurrent trades, 1,000 trades/day or business settlement outcomes. Current event timing separates event deltas by workflow waiting states, not a production profiler.
15. **Assets and network.** No remote fonts, analytics, LLM APIs or cloud resources are used by the UI. Development dependency downloads occur only during installation. The demo runtime needs no outbound internet.
